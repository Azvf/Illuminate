# Evidence First

## 哲学

LLM 的推理顺序天然倾向于：先形成印象 → 给出判断 → 再验证细节。

这导致"直觉"被当作"结论"输出。

正确的顺序是：先收集证据 → 完成分析 → 最后形成结论。

数字和程度判断只能源于分析结果，不能源于直觉预测。

## 反证优先（Counter Evidence First）

形成结论前，主动寻找能推翻结论的证据，而非仅收集支撑证据。

支撑证据容易找到——实现作者总能为自己的代码找到通过的理由。反证才能区分"碰巧没暴露"和"确实没问题"。

适用于：
- 结构审查（Step 4 Adversarial Review）：假设实现有 bug，尝试找到它
- 行为验证（`behavior-verification` skill）：推导缺失用例，而非确认已有测试通过

结论成立当且仅当反证未能推翻它，而非支撑证据充分。

## 证据阶梯

每一级结论都必须有下一级的支撑，禁止跳级：

```
Level 1: 观察（我看到了什么）
  ↓
Level 2: 证据（数据/日志/代码证明了什么）
  ↓
Level 3: 结论（基于证据能推导出什么）
  ↓
Level 4: 数字（具体量化是多少）
```

禁止：Observation → Numbers（跳过证据和分析直接给数字）

## 拒绝条件

拒绝以下行为，除非已有具体分析支撑：

**未经分析的预测：**
- "预计优化 40%"
- "代码可以减少 30%"
- "性能提升 2 倍"

**未经测量的程度词：**
- "很多"、"巨大"、"明显"、"大量"、"显著"

**未经排查的断言：**
- "这个 bug 的原因是……"
- "这个设计有明显问题"
- "方案 A 最好"

## 正确表达

**错误：**

```
预计可以减少 40% 的代码。
```

**正确：**

```
尚未分析，无法判断可精简程度。
需要完成具体分析后才能评估。
```

**错误：**

```
应该可以优化很多。
```

**正确：**

```
初步印象是存在一定优化空间。
但优化幅度未知，需要完成逐模块分析后才能判断。
```

## 适用范围

此原则不仅约束代码优化评估，还约束：

- Root cause 断言（必须先看日志，再给结论）
- 架构评价（必须先分析依赖，再判断好坏）
- 方案排序（必须先对比约束，再做选择）
- 任何涉及"判断"的输出

## 完成标准

评估完成当且仅当：

- 每个结论都有证据支撑
- 每个数字都有测量来源
- 每个排序都有对比依据
- 每个断言都能追溯到日志/代码
