# Root Cause First

遇到问题时，不要停留在症状层面。

从入口到失败点画出完整调用链，找到第一个偏离点。

每一环节必须标注：

- 输入与输出
- 是否经过日志/调试验证（已验证 / 仅代码推断）
- 如果有两个以上环节仅靠代码推断，先补日志或测试，不得继续向下推进

## 三段式区分

Symptom（症状）≠ Trigger（触发器）≠ Root Cause（根因），三者必须分开写清。

- **Symptom（症状）**：用户/测试能直接观测到的异常表现
- **Trigger（触发器）**：本次复现中使根因暴露的具体条件
- **Root Cause（根因）**：症结所在的本质缺陷（代码缺陷、设计缺陷、契约缺失）

每次只能有一个 root cause。如果结论中有多个"可能"，说明还没找到。

## 修复约束

修复必须 1:1 对应 Root Cause。如果修复影响范围超过 root cause 定位的模块，必须先说明为什么需要扩大范围。

## 完成标准

调查完成当且仅当：

- 只有一个 root cause
- Root cause 已通过日志/测试验证
- 修复与 root cause 1:1 对应
- 无残留假设
